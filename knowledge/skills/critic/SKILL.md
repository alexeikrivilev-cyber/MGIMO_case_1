# Навык critic — внутренний критик с изолированным контекстом

## Когда применять

- Артефакт шага 0–5 закрыт (навыки framing/evidence/options/
  strategy-*/verification/decisions отработали), перед коммитом или
  предрегистрированным замером пользы механизма.
- Задача BRIEF п.16 / TASK-hermes-4 §1: заменить отсутствующего внешнего
  эксперта внутренним критиком — и измерить, снижает ли механизм
  self-assessment bias.

## Главное правило: изоляция по конструкции

Критик НЕ имеет доступа к истории создания артефакта:

1. Свежая сессия (`opencode run`) — нулевой контекст.
2. Содержимое артефакта и рубрики передаются **инлайном в промпте** —
   критику не нужно ничего читать с диска; инструкция явно запрещает
   читать файлы проекта (STATE.md, LOG.md, черновики, другие артефакты).
3. Критик **read-only**: не правит артефакт, а возвращает оценки и
   findings; правки вносит автор-оркестратор.
4. Честная маркировка во всех отчётах: «внутренний критик», не внешняя
   экспертиза (внешних экспертов нет — BRIEF п.16).

Ограничение (называть явно): изоляция — на уровне сессии и промпта, не
sandbox; модель технически может попытаться читать файлы, поэтому
инлайновая передача + запрет в инструкции — обязательны.

## Метод

1. **Рубрика** — `eval/rubrics/hackathon-criteria.md` (1:1 из критериев
   хакатона, 4 × 10). Без рубрики критик не запускается: оценки без
   шкалы несравнимы между прогонами.
2. **Промпт** (шаблон — `scripts/run_critic.py`, режим `critic`):
   роль «внешний рецензент» + артефакт инлайном + рубрика инлайном +
   запрет читать файлы + формат выхода (оценки 1–5 по критериям, два
   прохода: щедрый/строгий; findings с важностью, местом, почему важно,
   что починит; 1–3 пункта «что сделано хорошо» с доказательством).
3. **Режим self** (для замера пользы механизма): тот же артефакт и
   рубрика, но роль «ты — автор этого артефакта, оцени себя по той же
   рубрике». Сравнение `critic` vs `self` на ОДНОМ артефакте и ОДНОЙ
   рубрике — и есть замер: расхождение оценок и findings, которые
   самооценка пропустила.
4. **Балансировка порядка**: артефакты чередуются (нечётные — сначала
   critic, чётные — сначала self), чтобы порядок прогона не был
   спутан с эффектом механизма.
5. **Предрегистрированное правило вывода** (до прогонов):
   - находка критика с важностью ≥ «важно», которой нет в self-выходе →
     механизм оправдан (self-assessment bias снижается);
   - MDD: расхождение по критерию ≥ 0.5 балла ИЛИ ≥ 1 важный
     пропущенный finding;
   - иначе — честный negative result: «critic не нашёл того, что
     пропустила самооценка на этих артефактах» (пишется наравне с
     положительными).
6. **Findings — результат, а не приписка.** Пустой список findings на
   артефакте с известными пробелами — сам по себе сигнал (либо артефакт
   чист, либо критик «щедрый»); сверяется с рубрикой вручную.

## Проверка

- Манифест прогона на месте: `eval/runs/critic-matrix/manifest.md` — у
  каждого артефакта два режима (`critic`, `self`) и оба exit 0;
- в выходах есть блок «## Оценки» (4 критерия, два прохода) и блок
  «## Findings» — формат рубрики соблюдён (иначе прогон не засчитан);
- метка прогона видна в COST.md (колонка «Шаг» = «О4: …»), $ посчитан;
- после прогонов роли: `git status` чистое, кроме строки COST.md и
  каталога прогона (критик read-only — проверено);
- замер пользы записан в `docs/research/measurements.md` §12 с
  предрегистрированным правилом вывода.

## Анти-паттерны

- Не давать критику LOG.md/STATE.md «для контекста» — это уничтожает
  измерение (критик начнёт оценивать намерения, а не артефакт).
- Не править артефакт по findings молча: каждое принятое finding →
  запись в LOG.md (что и почему), каждое отклонённое — с причиной.
- Не выдавать внутренний критик за внешнюю экспертизу ни в одном
  артефакте сдачи.
- Не гонять критика на черновиках: только на закрытых артефактах.
