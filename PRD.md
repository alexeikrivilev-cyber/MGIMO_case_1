# PRD — «Стратег»: папочный ИИ-агент для руководителя цифрового продукта

> Хакатон МегаФон «Фабрика Продуктов». Версия 1.1, 2026-11-16 (День 2).
> Статус: v1.1, согласован с OpenClaw (PO) — решения R1–R6 зафиксированы
> (§17). Этот документ — технико-продуктовое решение; исследования — в `docs/research/`.

---

## 1. Продукт в одном абзаце

«Стратег» — **репозиторий-папка** (инструкции + база знаний + шаблоны + скрипты проверки), которую руководитель продукта открывает в среде типа Cursor / Claude Code / GigaCode / Codex и ведёт в ней диалог с агентом. Агент проводит руководителя по пути: **размытый запрос → уточнённая задача → картина ситуации с источниками → ≥3 содержательно разных варианта (включая «оставить как есть») → согласованные продуктовая и коммуникационная стратегии → план проверки**, подключая человека на точек существенного выбора и не бросая после решения (основания, обязательства, пересмотр при новых данных). Это НЕ автономный агент и НЕ программа: вся «магия» — в файлах папки, работающих в любой совместимой среде.

Не-цели (явно): замена руководителя продукта; автономные действия от его имени; секреты и платные сервисы по умолчанию.

## 3. Архитектура папки (что фактически лежит в репозитории)

```
strategy-agent/
├── AGENTS.md                  # ПОСТОЯННЫЕ ИНСТРУКЦИИ: workflow, дисциплина доказательств,
│                              # где что лежит, предупреждения о стоимости. <200 строк, plain markdown.
├── README.md                  # для человека: как запустить за 5 минут
├── STATE.md                   # СОСТОЯНИЕ ЗАДАЧИ: Resume-карта (см. §6)
├── LOG.md                     # журнал действий + оснований (вкл. неудачи)
├── COST.md                    # учет стоимости прогонов (оба контура)
├── PRD.md                    # этот документ: решение, обоснования, риски
├── knowledge/                 # МЕТОДИЧЕСКИЕ ЗНАНИЯ (навыки, прогрессивная загрузка)
│   ├── index.md               # навигация: какой навык когда (§10)
│   └── skills/
│       ├── framing/SKILL.md           # постановка задачи
│       ├── evidence/SKILL.md          # сбор материалов, дисциплина источников
│       ├── options/SKILL.md           # генерация вариантов + возражения
│       ├── strategy-product/SKILL.md  # продуктовая стратегия
│       ├── strategy-comms/SKILL.md    # коммуникационная стратегия
│       └── verification/SKILL.md      # план проверки + пересмотр (§11)
├── project/                   # МАТЕРИАЛЫ ПРОЕКТА + СОСТОЯНИЕ ЗАДАЧИ
│   ├── brief.md               # рамка задачи (после шага 0)
│   ├── evidence/              # журнал фактов с источниками
│   ├── research.md            # картина ситуации + пробелы
│   ├── options.md             # варианты + возражения
│   ├── strategy-product.md
│   ├── strategy-comms.md
│   ├── verification-plan.md
│   ├── decisions.md           # решения post-decision (доп. уровень)
│   ├── materials/             # загруженные документы/таблицы (raw + выдержки)
│   └── council/run-*/         # протоколы Консилиума (§8)
├── scripts/                   # ДЕТЕРМИНИРОВАННЫЕ ПРОВЕРКИ (запускаются hook'ами и вручную)
│   ├── check_sources.py       # каждое существенное утверждение имеет ссылку
│   ├── check_options.py       # ≥3 варианта, status-quo, разделение факт/гипотеза
│   ├── check_state.py         # валидность STATE.md перед концом сеанса
│   └── cost_report.py         # сводка стоимости из COST.md
├── templates/                 # шаблоны артефактов (brief, options, strategy, plan)
├── eval/                      # наш измерительный стенд (§12, Дни 4–5)
│   ├── tasks/                 # демо-задача + отложенные задачи
│   ├── rubrics/               # expert-рубрики (критерии хакатона 1:1)
│   └── run_ab.py              # протокол попарного A/B с балансировкой порядка
├── docs/research/             # исследования (benchmarks, hypotheses, council, costs, ecosystem)
└── .gigacode/rules/*.md       # тонкий адаптер для GigaCode (портировка, §6)
```

Почему именно так (обоснование по исследованиям, `docs/research/agentic-ecosystem.md`):
- **AGENTS.md** — единственный формат, который читают все целевые среды (60k+ репозиториев, стандарт под Linux Foundation AAIF). Держим коротким: Generic context files не повышают корректность и добавляют >20% стоимости (arXiv 2602.11988); окупаются предупреждения о процессе/стоимости и неочевидные соглашения.
- **Навыки (skills)** — единственный стандартный способ держать большую методическую библиотеку вне контекста (~100 токенов в простое, <5k при активации). Куратированно: 4–6 навыков, т.к. точность выбора技能 коллапсирует при росте пула (29.6%→3.3% при 5→100).
- **Скрипты + hooks** — детерминированные гарантии, которые модель не может «согласовать» прочь; нулевая стоимость в контексте.
- **Файловое состояние** — «контекст = RAM, файловая система = диск» (Manus); Anthropic SDK: «не рассчитывайте на resume сеанса».

## 4. Workflow и точки подключения человека

```
Запрос РП
   │
   ▼
[Шаг 0] РАМКА ─────────────── ЧЕКПОИНТ 1 (человек подтверждает рамку)
   │  уточняем только то, что меняет следующий шаг (MINT: обратная связь ценна)
   ▼
[Шаг 1] МАТЕРИАЛЫ ────────── (человек может догрузить/отклонить источники)
   │  документы/таблицы/сайты из разрешённых источников → evidence с URL+датой
   ▼
[Шаг 2] ИССЛЕДОВАНИЕ ─────── ЧЕКПОИНТ 2 (человек утверждает план/перечень решающих вопросов)
   │  сопоставление источников; честные пробелы
   ▼
[Шаг 3] ВАРИАНТЫ ─────────── ЧЕКПОИНТ 3 (человек выбирает вариант или возвращает)
   │  ≥3 содержательно разных (+ «оставить как есть»), сильные возражения,
   │  Консилиум (§8) при высокой ставке
   ▼
[Шаг 4] СТРАТЕГИИ (продукт + коммуникация + план проверки)
   │
   ▼
[Шаг 5] ПОСЛЕ РЕШЕНИЯ (доп. уровень): decisions.md — владельцы, метрики,
      условия пересмотра; пересмотр при новых данных (§11)
```

Правила подключения человека: (1) не более 3 обязательных чекпоинтов на прогон (каждый прерывание измеряется — лишние — дефект); (2) агент всегда показывает прогресс и может быть остановлен на любом шаге; (3) на чекпоинте — короткая сводка «что известно / чего не знаем / что решаем», а не простыня.

## 5. Разделение знаний (4 слоя)

| Слой | Где | Когда грузится | Содержание |
|---|---|---|---|
| 1. Постоянные инструкции | `AGENTS.md` | всегда | workflow, дисциплина доказательств, пути, предупреждения о стоимости. Никакой энциклопедии |
| 2. Методические знания | `knowledge/skills/*` | по задаче (progressive disclosure) | наш метод: как ставить рамку, как вести доказательства, как генерировать варианты и возражения |
| 3. Материалы проекта | `project/materials/`, `project/evidence/` | just-in-time (по ссылке из артефакта) | сырые документы + выдержки с URL/датой; сжатие «обратимое» (храним URL, а не только пересказ) |
| 4. Состояние задачи | `STATE.md` + `project/*.md` | перечитывается на каждом шаге | где мы, что решено и почему, что открыто, что провалилось |

Обоснование: context rot (Chroma 2025: деградация даже на простом поиске при росте длины), 4 тактики Бройнига (quarantine/offload = наши слои 2–4), Codified Context (hot/cold memory). Порядок операций LangChain: изолировать → масштабировать; управлять → persist.

## 6. Продолжение после перерыва и переносимость

- **`STATE.md`** (схема по ATWZ + awesome-agentic-patterns): objective · текущий шаг · завершённые шаги · решения и причины · открытые вопросы · обязательства · ключевые файлы · провалившиеся подходы и почему · стоимость на сейчас. Журнал — append-only, свежие записи дословно.
- **Resume = новый чат, засеянный из STATE.md** (Anthropic SDK: «sessions persist the conversation, not the filesystem»; «don't rely on session resume»). Навык `resume` перечитывает STATE.md в контекст на старте сеанса (инъекция `` !`cat STATE.md` `` в Claude Code; в других средах — явное указание в AGENTS.md).
- **Недеструктивные чекпоинты**: запись состояния никогда не переписывает рабочий контекст.
- **Переносимость**: `AGENTS.md` — единый источник истины; тонкие адаптеры: `.gigacode/rules/*.md` (указатель), заметка в README для Gemini CLI (`context.fileName`). Навыки live in `knowledge/skills/` + симлинк/копия в `.claude/skills` / `.agents/skills` при необходимости. Ограничение: Codex режет объединённые инструкции до 32 KiB → AGENTS.md <10 КБ.

## 7. Прозрачность

- **`LOG.md`** — каждое действие: что сделано, на каких основаниях (ссылки на evidence), сколько стоило; **неудачи и тупики тоже пишутся** (Manus: «стирание неудачи удаляет evidence»).
- **`COST.md`** — каждый прогон: шаг, модель, токены (in/out/reasoning), поисковые вызовы, оценка $ по текущим прайсам (`docs/research/llm-pricing-agent-costs.md`). Hook дописывает автоматически.
- **Основания**: каждое существенное утверждение в артефакте имеет ссылку; `scripts/check_sources.py` блокирует артефакт без ссылок (hook, exit code 2).
- **Оценка vs факт**: `cost_report.py` сравнивает оценку стоимости с metered (модели систематически недооценивают свой расход — Stanford 2026: разброс до 30×).

## 8. Консилиум (оригинальная фича)

Полный дизайн и план измерений — **`docs/research/council-design.md`**. Ключевое:
- **Что это**: совет из 5 когнитивных линз (продукт, коммуникации, данные, адвокат дьявола, пользователь) для **дивергенции и критики**, не для консенсуса. Обоснование: дебаты подавляют разнообразие (arXiv 2609.00683), согласие worth less than disagreement (ACL 2026), «один писатель + read-only критики» — единственный Working паттерн (Cognition 2026).
- **Протокол**: замороженный общий бриф → независимая дивергенция (без кросс-чтения) → перекрёстная критика с квотами → защищённый адвокат дьявола → синтез единственным писателем с сохранением несогласия → чекпоинт человека.
- **Два контура**: dev — полная версия (все роли, протокол, гетерогенность моделей, все замеры); prod — оптимизированная (3 роли, один раунд, дешёвая модель для адвоката, кэш брифа, только высокие ставки), если замеры показывают сохранение качества.
- **Измерение**: diversity (семантическая дистанция) + качество возражений + качество стратегии (expert-рубрика) + стоимость; решение о включении в prod — по предрегистрированному правилу (council-design.md §6).

## 9. Routing (выбор процесса/модели/инструмента по задаче, качеству и стоимости)

| Шаг | Процесс | Модель (dev) | Модель (prod, предложение) | Почему |
|---|---|---|---|---|
| 0 Рамка | framing skill | frontier-mid | mid | диалог, цена ошибки низкая |
| 1 Материалы | evidence skill + веб-поиск | mid + cheap (извлечение) | cheap + mid | extraction-таски дешёвы |
| 2 Исследование | fan-out субагенты (read-only) | frontier + cheap workers | mid + cheap | Anthropic: fan-out даёт +90% на research-eval, токены объясняют 80% дисперсии |
| 3 Варианты | options skill (+ Консилиум при высокой ставке) | frontier, гетерогенно | mid, 3 роли | разнообразие — ресурс, нужен сильный seed |
| 4 Стратегии | strategy skills | frontier | mid→frontier по ставке | синтез — самое дорогое, решает качество |
| 4′ Проверка | verification skill | mid | cheap+mid | чек-листы |

ПравилоRouting-а: **retrieval до reasoning** (arXiv 2509.06861: с поиском масштарование compute даёт +11.8pp и −8.6pp галлюцинаций; без поиска — ноль). Effort по умолчанию medium; высокий — только на синтезе в dev. Каждое маршрутное решение логируется с причиной (аудируемо).

## 10. Skills / hooks / subagents / MCP — что оправдано (обоснование)

| Механизм | Решение | Обоснование |
|---|---|---|
| Skills (4–6, куратированно) | **ДА** | SkillsBench: +16.2pp в knowledge-heavy доменах; процедурные якоря; progressive disclosure. НЕ самосгенерированные навыки (−1.3pp); НЕ >6 навыков (retrieval collapse) |
| Hooks (2–4) | **ДА** | детерминированные гарантия (ссылки, STATE, COST, чек-лист опций); нулевая стоимость |
| Subagents (1–3, read-only, fan-out) | **ДА, узко** | изоляция контекста для шумного research-fan-out; такса 2.6–5.9× токенов — окупается только изоляцией, не «больше агентов» |
| Agent teams / messaging / dynamic workflows | **НЕТ** | overhead без measured value; не портируемы |
| MCP: веб-поиск/fetch (1 сервер) | **ДА** | единственная по-настоящему новая возможность (живые источники с цитатами); Brave (бесплатный тир) / Tavily |
| MCP: filesystem / GitHub / memory / Notion | **НЕТ** | нативные инструменты сред уже дают это; bloat: 96 тулов съели 57% окна (Amplitude); точность выбора падает >30–50 тулов |
| Slash commands | **НЕТ отдельно** | слиты в Skills |

## 11. База знаний и пост-решение

- **Навигация**: `knowledge/index.md` — карта «вопрос → навык»; поиск по формулировке/смыслу/связям — штатными grep/glob по markdown (векторное хранилище не нужно: Manus; материалы небольшого объёма).
- **Память между сеансами**: STATE.md + decisions.md + evidence; записи версионируются в git.
- **Исправление устаревших записей**: **не стирая** — append-only supersession с датой и причиной («govern before you persist», LangChain); hook проверяет, что новые артефакты ссылаются на актуальные версии.
- **Поддержка решений (доп. уровень)**: `decisions.md` — решение, владелец, метрика, условие пересмотра, дата; навык `verification` по расписанию/триггеру сверяет новые данные с основаниями и предлагает пересмотр (явно помечая, что изменилось).

## 12. Устойчивость к сбоям

| Сбой | Поведение |
|---|---|
| Поиск/фетч упал | retry с backoff → деградация: работа с локальными материалами + явная запись пробела; ссылка помечается «не проверена» |
| Модель вернула мусор/обрыв | артефакт не коммитится; шаг повторяется с другой моделью/effort; неудача пишется в LOG.md |
| Превышение бюджета (prod) | hook по COST.md останавливает прогон на пороге с сохранённым STATE (не потеря работы) |
| Битый STATE.md | `check_state.py` восстанавливает из последней валидной копии (git) или из артефактов project/ |
| Конфликтующие источники | оба фиксируются в evidence с конфликт-меткой; артефакт обязан показать конфлиль, а не «усреднить» |
| Среда без MCP | веб-шаг деградирует в «пользователь вставляет источники» — путь остаётся сквозным |

Заимствовано у GAIA2 (noise tolerance, ambiguity) и OSWorld 2.0 (документированные провалы агентов: потеря ограничений, пропуск mid-task информации, угадывание вместо вопроса пользователю, пропуск верификации) — наш STATE + чекпоинты + хуки адресуют каждый из этих пунктов.

## 13. Двухконтурная модель стоимости (уточнение владельца 2026-11-16)

| | Контур разработки (dev) | Контур прода (prod) |
|---|---|---|
| Бюджет | **не ограничен** — гоняем всё, что даёт знание (дорогие бенчмарки, полный Консилиум, frontier-модели) | стоимость одного прогона на пользователя — **целевая метрика** |
| Что оптимизируем | выявить лучшее | лучшее соотношение качество/стоимость |
| Консилиум | полная версия (все роли, протокол, гетерогенность, все замеры) | оптимизированная (3 роли, 1 раунд, дешёвая модель адвоката, кэш), **только если замеры позволяют** |
| Учёт | каждый прогон в COST.md; итог: «сколько стоило исследование» | $/run по шагам; цель (предложение к обсуждению): **≤$2–5 за полный прогон** на mid-tier, council-off режим ≤$1 |

Ориентиры стоимости (источники — `docs/research/llm-pricing-agent-costs.md`): deep-research задачи $0.92–$10/вызов (o3-DR ~$10, o4-mini-DR ~$0.92, на DeepResearchBench $1.27±0.26, Google self-estimate $1–3/task standard); enterprise agent task $0.21 blended (14.2K токенов); наш полный прогон — 10–30 вызовов моделей + поиск → оценка $1–6 в prod-конфигурации (пересчитаем по факту на Дне 5).
**Сравнение (требование ТЗ):** ручной аналитик (часы × ставка), обычный чат (без доказательств/состояния/учёта), коммерческие deep-research ($1–10/отчёт) — замеряем на демо-задаче: время, rubric coverage, citation accuracy, $ (протокол — `benchmarks.md` §3).

## 16. Конфликты ТЗ ↔ требований владельца (назованы, как требовалось)

1. **«Экономичность» ТЗ vs «в разработке не экономить»** → двухконтурная модель (§13): экономика — метрика прод-агента, не исследований.
2. **«Каждая фича с бенчмарком» vs 5 дней** → полные бенчмарки — для mandatory-пути и ключевых фич; для остальных — proxy-замеры с явной пометкой «proxy, не benchmark».
3. **«Консилиум» владельца vs «число агентов не преимущество» ТЗ** → council — измеримая фича с предрегистрированным правилом демоции; при отсутствии выигрыша идёт дешёвый эквивалент (H2/H4).
4. **«Менять подходы» vs 5 дней** → research-гипотеза попадает в продукт только после замера пользы; negative results тоже пишем (п.3 владельца: «чтобы не ходить по кругу»).
5. **Persona-роли vs evidence** → роли как когнитивные линзы, не как заявка на точность (H1).

## 17. Решения OpenClaw (PO) — зафиксированы как R1–R6 (2026-11-16, v1.1)

Ниже — решения, принятые PO по итогам обсуждения §17 v1.0; они обязательны
к исполнению (источник: TASK-hermes-2.md, раздел «Решения PO»).

1. **R1. Двухконтурный бюджет — подтверждён.** Dev без ограничений; каждый прогон пишется в `COST.md` (шаг, модель, токены in/out/reasoning, поисковые вызовы, оценка $ по прайсам из `docs/research/llm-pricing-agent-costs.md`). 4. **R4. Навыки vs монолит — подтверждено:** 4–6 куратированных навыков, `AGENTS.md` <200 строк и <10 КБ, plain markdown (Codex режет до 32 KiB, оставляем запас). *Факт исполнения (О2): навыков 7 — шаг 2 описан разделом в навыке  `evidence` вместо отдельного навыка `research`; расхождение с ориентиром «4–6» доложено OpenClaw, кандидат на слияние при жёстком лимите — `strategy-comms` в `strategy-product`.*
5. **R5. Доступы:** без внешних ключей. Dev-прогоны — через Hermes (stepfun) и OpenCode (установлен, serve на 127.0.0.1:4096). Целевая среда демо — **OpenCode**; Cursor / Claude Code / Codex / GigaCode не установлены — smoke-матрицу портируемости (B12) делаем по документации + эмуляцию ограничений (Codex 32 KiB) позже, демо-видео снимаем в OpenCode.
