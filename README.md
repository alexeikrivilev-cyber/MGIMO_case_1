# strategy-agent — «Стратег Фабрики продуктов»

Папочный ИИ-агент для руководителя цифрового продукта: репозиторий с
инструкциями, базой знаний и инструментами, который ведёт от размытого
запроса («почему падает удержание») до обоснованной продуктовой и
коммуникационной стратегии — и остаётся с ним после принятия решения
(реестр решений, план проверки, пересмотр при новых данных).

Это **не программа и не автономный агент**: это папка, которую открывают
в средах типа Cursor / Claude Code / GigaCode / Codex / OpenCode
(единый формат инструкций — `AGENTS.md`). Хакатон «Фабрика Продуктов»
(МегаФон), кейс «Стратег Фабрики продуктов».

Демо-проект (задача РП, открытые данные, все артефакты полного пути) —
в [`project/`](project/README.md). Измерения, на которых держатся
решения об архитектуре, — в [`docs/research/measurements.md`](docs/research/measurements.md).

## 0. Коротко: почему этот проект решает задачу

Кейс требует агента, который превращает размытый запрос руководителя в
обоснованную стратегию с планом проверки. Обычное решение хакатона —
промпт и, может быть, пачка скриптов. Наше отличие в том, что **каждое
архитектурное решение измерено, а каждое числовое утверждение в
артефактах проверяемо машинно**:

1. **Разрыв «чат → агент» измерен, а не заявлен.** На замороженном брифе
   и на held-out задаче: обычный чат 24/25 из 40 по типовой рубрике,
   полный продукт 39/40 и 40/40 (§23.5). При измеренном шуме судьи
   (sd 1.03, MDD 4.08) это на порядок выше шума.
2. **Прирост несут инструкции и навыки, не число агентов.** Абляция
   слоёв L0→L4 (прямой вызов API, изолированная среда): +AGENTS.md
   даёт +6/+7, +навыки +7/+6 по типовой рубрике; остаток «продукт
   поверх гейтов» — на границе шума (+4.0 ± 4.1 при k=3, интервал
   накрывает 0). Поэтому продукт — не «оркестратор из восьми агентов»,
   а workflow + знания + проверки.
3. **Числа без основания не проходят.** 14 детерминированных гейтов
   (в т.ч. «ссылка есть, а содержания нет», «диапазон без основания»,
   «перенос цифр аналога на сервис») встроены в хук: агент физически
   не может записать артефакт с непроверяемым фактом. Реальный лог
   прогона с падениями и ревизиями — `eval/runs/t18-case-launch.log`.
4. **Критик работает как детектор, а не «улучшатель».** Четыре
   независимых измерения улучшающих гипотез не дали прироста выше шума
   (§22.4/§22.7/§23.6/H-C2); как детектор дефектов он даёт 44 находки
   на артефактах шагов 4–5, ~93% из которых подтвердились при ручной
   разборке. Отрицательные результаты опубликованы, не спрятаны.
5. **Человек-судья — главный ground truth.** 10 слепых пар с ослеплением
   по seed и ключом после суждения: суждение человека определило выбор
   конфигурации навыков (курация 3-0 над lean), который замеры оставили
   нерешённым (измеримого различия нет при k=3). Полная матрица вердиктов
   с основаниями, оговорками и тем, что она изменила в продукте —
   `eval/runs/t13-blindpairs/verdict-matrix.md`. Первая отправка пар была
   дайджестом (срез 1100 символов) — дефект предъявления назван и
   исправлен, вердикты взяты только по полным текстам.
6. **Продолжение после перерыва — не обещание, а прецедент.** Внешний
   SIGINT убил сессию посреди task 18 — коммит `98d17d6` несёт это в
   сообщении; работа возобновлена новым чатом из `STATE.md` и доведена
   до зелёного (`3b0cc84`, журнал — `eval/runs/t18-case-heldout/manifest.md`).
   Оговорка по фактам, а не по форме: сам демо-прогон шёл непрерывно —
   это названо в его собственном артефакте
   (`eval/runs/t18-case/artifacts/decisions.md`), а возобновление
   продемонстрировано held-out прогоном отдельными сессиями. Ссылки на
   коммиты даны по текущей истории: при выведении сырья прогонов из git
   (2026-11-18) хеши всех коммитов изменились.
7. **Экономика прозрачна по строкам.** Каждая сессия учтена в `COST.md`
   хуком на сообщение; полный демо-путь — $2.67 (22 сессии, включая
   ревизионные раунды), весь проект — $59.31. Потери и отвергнутые
   прогоны учтены как затраты, не спрятаны.
8. **Субстанция вместо вайбкодинга.** Все четыре критерия ТЗ закрыты
   маппингом «требование → артефакт → проверка» (§5), и этот маппинг
   можно проверить командами из §1.1 без ключей и без оплаты.
9. **Длинный диалог с РП не деградирует — измерено, не заявлено.** 12
   поворотов в ОДНОЙ сессии (контекст 70.9K → 81.9K токенов): 0 контрадикций
   с артефактами после разбора 35 сырых находок, memory-пробы на поворотах
   3/6/11 совпадают дословно, доля grounded чисел 1.00 → 1.00 (§2, строка
   13). Контрольная рука — свежая сессия на каждый вопрос — дала БОЛЬШЕ
   сырых находок, чем длинная сессия: находки были свойством вопросов и
   измерителя, не длины диалога. n=1 на руку = suggestive. Пример цепочки —
   `examples/long-dialogue.md`.

## 1. Быстрый старт

### 1.1 Проверить репозиторий — без ключей и без оплаты

Всё, что агент производит, проверяется детерминированными гейтами и
тестами; они не требуют ни ключей, ни сети. Единственная сторонняя
зависимость — `pytest` (для тестов); все гейты и скрипты работают на
стандартной библиотеке:

```bash
python3 -m venv .venv && . .venv/bin/activate    # изолированное окружение (один раз)
python3 -m pip install -r requirements.txt        # единственная зависимость — pytest
python3 -m pytest tests/ -q                                   # 517 тестов
python3 scripts/check_sources.py project/brief.md project/research.md \
  project/options.md project/strategy-product.md \
  project/strategy-comms.md project/verification-plan.md \
  project/decisions.md                                        # каждый факт несёт основание
python3 scripts/check_evidence_links.py --task all            # число → содержание evidence
python3 scripts/check_acceptance.py project/strategy-product.md \
  project/strategy-comms.md project/verification-plan.md \
  project/decisions.md     # приёмный чек-лист 6 вопросов — на каждом артефакте этапа 4–5
python3 scripts/check_actionability.py project/strategy-product.md \
  project/strategy-comms.md project/verification-plan.md \
  project/decisions.md     # структурные признаки плана (P0–P2, контрольные группы, KPI, остановка)
python3 scripts/cost_report.py                                # сводка расходов
```

Демо читается напрямую: `project/README.md` → `project/brief.md` →
`research.md` → `options.md` → `strategy-product.md` →
`strategy-comms.md` → `verification-plan.md` → `decisions.md`.

### 1.2 Запустить агента — что нужно заранее

| Что | Зачем | Обязательно? |
|---|---|---|
| Python 3.10+ (желательно venv) + pytest (`requirements.txt`) | тесты и гейты | да |
| Node.js 18+ | плагин хуков (`.opencode/`) | да для прогона агента |
| OpenCode CLI (`opencode`, проверено на 1.19.5) | целевая среда запуска | да для прогона агента |
| **Ключ StepFun API** (`STEPFUN_API_KEY`) | **платный сервис**: модель `stepfun/step-5-preview`, ~$1.00/M input, ~$2.70/M output (прайс — `docs/research/llm-pricing-agent-costs.md` §1.8) | да для прогона агента; ключ только через env, никогда в репозиторий |

Другие провайдеры возможны: модель и baseURL задаются в
`.opencode/opencode.json` (сейчас — StepFun через OpenAI-совместимый
эндпоинт). Скрытых настроек нет: конфиг лежит в репозитории, все
секреты — через окружение.

```bash
# 1. Ключ — только через окружение (в репозиторий не попадает):
export STEPFUN_API_KEY=<ключ StepFun>

# 2. Зависимости плагина хуков (один раз, из корня репозитория):
cd .opencode && npm install && cd ..

# 3. Прогон агента из корня репозитория:
opencode run "Выполни шаг 0 (рамка) по демо-задаче eval/tasks/demo-retention/task.md"
```

Что происходит внутри: инструкции грузятся из `AGENTS.md`; навыки —
из `knowledge/index.md` по шагу; после каждой записи `project/*.md`
хук `.opencode/plugins/strategy-hooks.ts` прогоняет гейты
(`check_sources`, `check_transferability`, `check_ranges`,
`check_complexity`; на артефактах этапа 4–5 — `strategy-product.md`,
`strategy-comms.md`, `verification-plan.md`, `decisions.md` — ещё
`check_acceptance` и `check_actionability`: область действия исправлена
в TASK-hermes-20, прежде гейты смотрели только на strategy-product.md,
и остальные артефакты этапа дошли до сдачи без плана); на каждом
сообщении ассистента хук дописывает строку учёта в прод-таблицу
`COST.md`; состояние шага агент ведёт в `STATE.md` и журнале `LOG.md`
(создаются прогоном в рабочей копии, в репозитории не хранятся) —
прерванный прогон продолжается новым чатом
(`opencode run "Прочитай STATE.md и LOG.md (навык resume) и продолжи"`).

Сколько стоит: одна сессия шага — **$0.04–0.30** (разброс по метке
`t18-case`, шаг с раундами ревизии — сумма его сессий). Измеренный
полный путь демо-кейса — **$2.67 за 22 сессии** (метка `t18-case` без
префикса `ho-`; разбор по строкам — `COST.md`), то есть ориентир ТЗ
«полный прогон mid-tier ≤$2–5» выполнен на полном прогоне, а не на
усечённом. Плюс раунд доводки артефактов шагов 4–5 до гейтов чек-листа
и плана после прогона — 7 сессий, $0.44 (метка `t20-gate-rev`): итог
поставленного результата — $3.11 за 29 сессий.

### 1.3 Полный путь кейса целиком (как в демо)

Демо-прогон, артефакты которого лежат в `project/`, воспроизводится
драйвером `eval/run_full_case.py` (шаги 0–5, гейты с явными кодами
возврата, ревизионные раунды по выводам гейтов, критик-детектор на
шагах 4–5, идемпотентность переиспользования зелёных артефактов):

```bash
export STEPFUN_API_KEY=<ключ StepFun>
python3 eval/run_full_case.py --task demo-retention --dry-run   # показать план, не тратить
python3 eval/run_full_case.py --task demo-retention             # прогнать
```

Журнал прогона (какие сессии, какие раунды ревизии, коды гейтов,
sha256 артефактов) — `eval/runs/t18-case/manifest.md`.

## 2. Почему агент устроен именно так: программа исследований

Архитектура — не выбор «по вкусу», а вывод из 20 задач стенда, каждая
с предрегистрацией (гипотеза и правило вердикта — ДО прогона). Полные
протоколы — `docs/research/measurements.md`; здесь — программа и
результаты, которые определили устройство.

### 2.1 Что мы тестировали и что узнали

| # | Вопрос | Метод | Результат | Что из этого следует в архитектуре |
|---|---|---|---|---|

L0→L1 +6/+7, L1→L2 +7/+6, L2→L3 прироста нет, L3→L4 на границе шума | прирост несут инструкции и навыки; «остаток агента» не многократный |

| 9 | Можно ли доверять самооценке? | Два изолированных критика на эквивалентных форках + суждение владельца (§30) | воспроизводимость выбора есть; вердикт по предрегистрации «не подтверждён» (покрытие 2 пары из 10) | оценка названа proxy; человек-судья — ground truth |

### 2.2 Дефекты, которые нашли сами прогоны (и как закрыли)

Стенд ломался, и это — часть результата: каждый дефект найден живым
прогоном, закрыт по классу, с регрессией:

- **Потеря финального текста сессии** на границе CLI/провайдера (exit 0,
  пустой выход): контракт переведён на инлайн-передачу входов, добавлен
  порог годности артефакта — теперь пустой вывод валит прогон.
- **Пустой выход критика при exit=0**: раньше давал ложный «зелёный» —
  теперь гейт падает (+тест).
- **Парсер частичной оценки** менял знак Δ серии — исправлен, серия
  пересчитана.
- **Дефект изоляции стенда** (§23.0): `.opencode/opencode.json`
  внедряет AGENTS.md в каждую in-repo сессию, поэтому A/B-руки шли на
  уровне L1+; верифицирован пробой, операционное правило — чистый
  L0/L1 только прямым вызовом API.
- **Гонка метки прогона** в хуке стоимости — вынесена в `eval/.cost-label`.
- **Класс «сообщение о работе без диффа»** — 7 преждевременных коммитов
  зафиксированы аудитами в measurements.md (§24.0 и др.), работа
  выполнена по факту; правило приёмки теперь требует сверки сообщения
  коммита с диффом.

Провальные и отвергнутые прогоны сохранены и опубликованы
(`...-contaminated{,2,3,4}/DEFECT.md`, потерянные сессии в COST.md),
не спрятаны.

## 3. Архитектура

Слои (принцип «порядок в знаниях» — постоянные инструкции, методика,
материалы проекта и состояние задачи хранятся раздельно):

| Слой | Где | Что |
|---|---|---|
| Постоянные инструкции | `AGENTS.md` | workflow с шагами 0–5 и чекпоинтами, границы, дисциплина доказательств; рабочий черновик — `docs/agents-md-staged.md` |
| Методические знания | `knowledge/skills/*` | 9 навыков (framing, evidence, resume, options, strategy-product, strategy-comms, verification, critic, decisions); карта «вопрос → навык» — `knowledge/index.md`; черновики — `knowledge/skills/_draft/` |
| Шаблоны | `templates/` | по файлу на артефакт шага |
| Состояние задачи | `STATE.md` + `LOG.md` | resume-карта и журнал действий (append-only) |
| Прозрачность стоимости | `COST.md` | dev/prod контуры, хук `cost-append` |
| Материалы проекта | `project/` | рамка, evidence, артефакты пути |
| Гейты | `scripts/check_*.py` | 14 детерминированных проверок (см. §1.1 и таблицу ниже) |
| Хуки | `.opencode/plugins/strategy-hooks.ts` | гейты на записи `project/*`, индекс навыков, `STATE.md`; учёт стоимости на каждом сообщении |
| Стенд измерений | `eval/` | рубрики 1:1 из критериев хакатона, A/B-руки, полный путь, критик-детектор, ось слепых зон; бенчмарк DABstep в Docker |
| Самоулучшение навыков | `product/agent/` | журнал мутаций (блобы sha256), предохранитель «только по замеру», откат fail-closed |

Процессы: агент ведёт РП по шагам (рамка → материалы → исследование →
варианты → стратегии → решения), на существенном выборе подключается
человек (чекпоинты 1–3), после решения — реестр решений с условиями
пересмотра. Работа с контекстом: входы артефакта передаются сессии
инлайном (файлы не открываются — контракт сессий, устраняющий потерю
выхода на границе CLI/провайдера), большой промпт режется
`chunk_prompt` (защита от E2BIG).

Гейты и что именно они ловят:

| Гейт | Класс дефекта |
|---|---|

## 4. Ключевые решения (каждое — с замером)

1. **Прирост несут инструкции и навыки, не число агентов.** Абляция
   слоёв L0→L4 (§23.5): обычный чат 24/25, +AGENTS.md 30/32, +навыки
   37/38, +проверки-гейт 37/36, полный продукт 39/40 по типовой
   рубрике; held-out: 25→32→38→36→40. Остаточная дистанция L3→L4 —
   на границе шума (+4.0 ± 4.1 при k=3, интервал накрывает 0) →
   развилка закрыта.
2. **Гейты — детектор, не оценщик.** Гейт проверок не поднимает балл
   (−2.00 ± 4.06), но ловит реальные структурные дефекты: 44 находки
   на артефактах шагов 4–5, ~93% подтверждены при ручной разборке.
3. **Критик — детектор с изолированным контекстом, не «улучшатель».** Четыре
   независимых измерения улучшательных гипотез не дали прироста выше
   шума (§22.4/§22.7/§23.6/H-C2/H-SI1). Оставлен как детектор: находить
   слабые места до человека.
4. **Консилиум: полный — в разработке, council-lite — в проде.**
   council-lite бьёт базу на обеих задачах (+4/+4, §14); полный
   протокол на held-out дал +2 < MDD при цене 5.7× → прод-кандидат
   council-lite, полный — dev-инструмент (§16). Триггер «высокая
   ставка» — 10/10 срабатываний, 0 пропусков.
5. **Человек-судья — главный ground truth.** 10 слепых пар (ослепление
   по seed, ключ после суждения): skill 2-0 в вилках прод-конфига,
   курация навыков 3-0 над lean; обычный чат выиграл 3:1 в парах, где
   отвечал на вопрос целиком (вход назван неэквивалентным — артефакт
   шага 3 намеренно останавливается на вариантах). Отсюда решение:
   шаги 4–5 ответственны за «готовность к действию» — план, метрики,
   критерии остановки.
6. **Аддендум критика не валидирован.** Пункты слепых зон подняли
   согласие с человеком 1/7 → 4/7, но перевернули контрольную пару →
   вердикт по предрегистрации: НЕ ВАЛИДИРОВАН (§30.2). Ось остаётся
   диагностикой; итоговый балл — база 1:1.
7. **Самоулучшение навыков — только по замеру.** Предохранитель
   `product/agent/skill_guard.py` требует артефакт замера до записи
   (негативный контроль: заметка вместо замера → отказ). Механика
   версионирования/откат — из изучения Hermes, адаптирована.
8. **Шаг 3 в проде — база (навык options) + критик-детектор на шагах
   4–5.** council-lite и critic-loop2 на шаге 3 проиграли базе в
   суждениях человека (сходится с замерами).
9. **Дефекты стенда находились живыми прогонами и исправлялись по
   классу**: потеря финального текста сессии на границе CLI/провайдера
   (контракт переведён на инлайн входы + порог годности артефакта),
   пустой выход критика при exit=0 (гейт), парсер частичной оценки
   (менял знак Δ серии), гонка метки прогона (вынесена в
   `eval/.cost-label`). Провальные и отвергнутые прогоны сохранены и
   опубликованы, не спрятаны.

## 6. Экономичность (время и расходы)

- **Полный путь демо-кейса** (шаги 0–5, прод-конфиг): 22 сессии,

  раунды ревизии по находкам гейтов и критик на шагах 4–5. Ориентир ТЗ
  «полный прогон mid-tier ≤$2–5» — выполнен. Сессии идут
  последовательно с гейтами между ними, поэтому машинное время прогона —
  порядок нескольких часов; участие человека — чекпоинты 1–3 и
  утверждение на шаге 4.
- **Корректировочный раунд после прогона** (TASK-hermes-19/20): 7 сессий,

  за 29 сессий. В суммы входят и потерянные прогоны дефектного контракта
  сессий — учтены как затраты, не спрятаны.
- **Одна сессия шага**: $0.04–0.30 (разброс по метке `t18-case`;
  кэш префикса даёт естественную экономию ~$0.18/руку — замер §19.3).
- **Весь проект** (разработка + все замеры, оба контура): **$59.31**
  по `cost_report.py` на момент сдачи; dev-контур без ограничений по
  правилу владельца, но каждая строка учтена.
- **Held-out полный путь** (симметрия демо, задачу «ДомКниг»): 23 сессии,
  $3.00 (метка `t18-case-ho-`) — первый запуск потерян дефектом
  «пустой выход», возобновление зелёное
  (`eval/runs/t18-case-heldout/manifest.md`).
- Обычный чат на том же брифе: $0.06 (замер B11) — но без оснований,

  абляцией, а не заявлен.

## 7. Удобство

- **Остановить**: прерывание в любой момент (Ctrl-C / внешний kill) —
  состояние в `STATE.md`, продолжение новым чатом без потери шага
  (реальный прецедент — возобновление task 18 после SIGINT).
- **Уточнить**: чекпоинты 1–3 — короткая сводка «что знаем / чего не
  знаем / что решаем», агент не проходи́т их молча.
- **Исправить**: гейты показывают строку и причину; ревизионные
  правки точечные (`scripts/apply_revision.py` с integrity-гейтом:
  заголовки, «оставить как есть», размер ≥60%).
- **Понять, что делает агент**: прогресс виден (манифест прогона,
  журнал LOG.md, строки стоимости в COST.md), каждый вывод несёт
  основание, пробелы названы явно.

## 8. Ограничения (названы, не спрятаны)

- **Оценка качества — self-assessed proxy.** Внешних экспертов нет;
  критик с изолированным контекстом — внутренний механизм.
  Изоляция — уровня промпта, не sandbox: сессия с инструментами в
  принципе может читать файлы (прецедент зафиксирован, ущерба не было).
- **Демо-сервис вымышленный.** «МегаТВ Онлайн» — сценарий; данные —
  открытый датасет-аналог (IBM Telco Churn). Перенос драйверов на
  стриминг — [гипотеза], денежные показатели аналога не переносятся
  (гейт `check_transferability`).
- **Денежный ROI не посчитан намеренно**: ARPU и суммы spend'ов
  неизвестны — экономика дана в структурных единицах (п.п. удержания,
  спасённые подписно-месяцы).
- **Шум измерений**: правило «n=1 = suggestive»; шум судьи измерен
  (sd 1.03), MDD пересчитан из него; часть клеток серий — на границе.
- **Held-out прогон полного пути** (`eval/runs/t18-case-heldout/`):
  первый запуск потерял шаг 3 — две сессии вернули пустой выход при
  exit=0 (дефект класса «пустой выход», $ учтены); возобновление прошло
  весь путь зелёным (23 сессии, $3.00, метка `t18-case-ho-`;
  ревизионные раунды: options ×2, strategy-product ×4, comms ×1,
  verification-plan ×1, decisions ×1 + критик-детектор на шагах 4–5).
  Итог — в его manifest.
- **Видео** записывает и выкладывает владелец (решение 2026-11-17);
  сценарий съёмки — `docs/submission/видео-сценарий.md`. Описание работы
  (PDF, 6 разделов ТЗ) — `docs/submission/описание-работы.pdf`, сборщик —
  `docs/submission/build_submission_pdf.py`.
- **Целевая среда** — OpenCode CLI; другие среды работают через
  `AGENTS.md` (портируемость описана, но матрица сред неполная —
  `docs/portability.md`).

## 9. Проверяемость: как убедиться в каждом утверждении

Репозиторий устроен так, чтобы **любое утверждение можно было проверить
командой или файлом, а не поверить на слово** — в том числе автоматически
(жюри, ИИ-ассистент, ревьюер). Правило простое: у каждого заявления в
README есть путь проверки.

| Утверждение | Как проверить |
|---|---|
| «517 тестов зелёные» | `python3 -m pytest tests/ -q` (без ключей, без сети; зелёное и в свежем клоне — TASK-hermes-21; 3 пропуска сида руки B устранены фолбэком на отслеживаемую копию — TASK-hermes-25) |
| «Гейты ловят дефекты» | `python3 scripts/check_sources.py <файл с числом без основания>` — ненулевой код возврата; негативные Controls в тестах |
| «Артефакты демо зелёные» | команды §1.1 на `project/*.md` — exit 0 |
| «Каждое число несёт основание» | `check_evidence_links --task all` — число резолвится в cited ev-N |
| «Полный путь воспроизводим» | `eval/run_full_case.py --task demo-retention --dry-run` — план без трат; журнал реального прогона — `eval/runs/t18-case/manifest.md` |
| «Расходы учтены полностью» | `python3 scripts/cost_report.py` — итог по контурам ($59.31); демо-путь: `grep -c "t18-case" COST.md` и суммы по меткам |
| «Прирост измерен, не заявлен» | `docs/research/measurements.md` §23.5 (абляция), §24.1 (k=3), §22 (детектор) — с предрегистрациями и MDD |
| «Отрицательные результаты не спрятаны» | measurements.md: §30.2 (аддендум НЕ валидирован), §22.7/H-R2 (второй раунд ревизии деградирует), §23.6 (порог правок r=+0.23) |
| «Секретов нет» | `.opencode/opencode.json` — `{env:STEPFUN_API_KEY}` (значение только из окружения); `git log -p --all | grep -cE "sk-[A-Za-z0-9]{20,}"` → 0. Простой `grep "sk-"` для этой проверки НЕ годится: он матчит `task-`, `ask-matt`, `disk-based` (25 совпадений в истории, ни одного — ключ) |
| «Продолжение после перерыва работает» | прецедент task 18: возобновление зафиксировано в manifest прогона (`eval/runs/t18-case/manifest.md`) |
| «Пример диалога — не выдумка» | `examples/dialogue.md` + `examples/proof.md`: каждая цитата отсылает к файлу записи, хеши артефактов сверяемы (`sha256sum`), метки стоимости различимы (`t18-case` vs `t18-case-ho-`) |
| «Длинный диалог не деградирует» | `examples/long-dialogue.md` (12 поворотов одной сессии) + `eval/runs/t23-longdialogue/summary.md`: предрегистрация ДО прогонов, три руки с контролем, метрики M1–M5, вердикт по правилу; пересчёт — `python3 eval/score_long_dialogue.py` |

Состав репозитория и что в нём намеренно НЕТ:

- **В git — только нужное организаторам:** инструкции (`AGENTS.md`),
  знания (`knowledge/`), шаблоны, гейты и драйверы (`scripts/`, `eval/*.py`),
  тесты, демо-проект (`project/`), курируемые доказательства измерений
  (манифесты прогонов, финальные гейты, находки критика, тексты слепых
  пар, регрессионные фикстуры), документы (`docs/`), описание и
  сценарий сдачи (`docs/submission/`).
- **Не в git (воспроизводимо прогоном, `.gitignore`):** сырые выводы
  моделей (`*.out`), логи сессий (`*.err/.start/.end/*.jsonl`), сырьё
  задач и бенчмарков (перекачиваемо по URL из скриптов), резервные копии
  артефактов до ревизии (`*.critic-backup`), `node_modules`, кэши.
  1303 таких файла выведены из-под git при сдаче (2026-11-18).
- **Логи прогонов, которые оставлены,** — курируемые: manifest, сводки,
  финальные гейты, находки; служебные хвосты сессий убраны как
  воспроизводимые и бессодержательные.
- **Точечные исключения под тесты (TASK-hermes-21):** чтобы `pytest`
  был зелёным в СВЕЖЕМ клоне, в git добавлены только файлы, которые
  читают тесты, — анализируемый CSV held-out
  (`bank-additional-full.csv`, основание ev-001…ev-007) и выходы Phase 2
  ролей прогона Консилиума (доказательство квот R1–R3). Остальное
  сырьё прогонов заменено фикстурами `tests/fixtures/` с записанными
  значений. Итого tracked — 424 файла (полоса ~375±30, верхняя граница 405:
  +19 сверх неё — предрегистрация, дословные ответы 36 поворотов
  эксперимента TASK-hermes-23, разбор находок M1, матрица слепой оценки
  (`eval/runs/t13-blindpairs/verdict-matrix.md`) и пример-цепочка
  `examples/long-dialogue.md`; это первичные данные эксперимента и
  human ground truth, без которых M1–M3 и вердикты судьи не пересчитать).
